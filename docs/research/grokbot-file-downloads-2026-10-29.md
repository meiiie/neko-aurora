## Behavior

The old HTTP handler could send the beginning of one file version and the end of another when the source changed during streaming. The new [snapshot preparation](../../app/native/internal/computer/download.go) copies into a private temporary file, checks identity/size/modification time and a second content hash, then sends attachment headers and the stable snapshot. Changes detected during preparation return an error before a download is offered. Later writes to the original cannot alter the staged response.

Temporary files are owner-only before any bytes are written, using the existing privatefs implementation. One snapshot is bounded by the configured Computer home-size quota (default 256 MiB); a manager permits two active downloads, with a cooperative 30-second preparation deadline. Closing a download deletes its temporary file and releases admission. Cancellation and ordinary failures clean up staged data. The [HTTP handler](../../app/native/internal/aurora/computer.go) preserves the original filename and supplies size, content hash, no-store and workspace/bot identity headers. Optional workspace fencing rejects mismatches; legacy direct links remain supported. Error responses contain no attachment headers or raw filesystem paths.

The [browser helper](../../app/native/internal/web/assets/app/downloads.js) is used by chat file chips and binary files in the Computer view. It checks same-origin routing, response identity/type/size and complete body length before handing a blob to the browser. It reports changed files, quota, busy and generic transport errors without navigating away or retrying. Duplicate clicks share one pending request; two distinct preparations are allowed. The 120-second client deadline bounds waiting. Results are discarded if their workspace or originating view has changed. The success wording only confirms handoff to the browser. Modified clicks retain native link behavior.

## Limits

Two-pass hash and identity validation is not an atomic filesystem snapshot against an adversarial writer. Filesystem open/stat calls are not forcibly cancellable, and a crash can leave owner-only temporary data. Client checks do not recalculate the SHA256 digest. Chrome acceptance here uses synthetic APIs; it does not prove native WebView/physical-device behavior, paid cloud transport, OS save-dialog completion or arbitrary network conditions. Windows filesystem and HTTP tests separately exercise the actual backend.

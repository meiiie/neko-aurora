# Versioned local task controls

`POST /v1/task-controls` uses the existing local session cookie, owner scope and same-origin boundary. It accepts `version: 1`, `requestId`, `expectedEpoch`, `expectedRevision`, `action`, `clientNonce`, and `text` only for supplement/replace. Both counters are required. `expectedRevision` matches `Work.taskRevision`, which defaults to zero. A committed command advances taskRevision; an unchanged runtime epoch during supplement cannot admit an old offline command. A command nonce is global to this local store, immutable and limited to 2048 retained receipts. Same nonce/body returns current linked work without granting new authority; changed body or stale counters returns 409. Pending UI commands must preserve their original counters, content and nonce.

Snapshot capability `local_task_controls_v1` advertises this endpoint; `queued_task_pause_v1` states its pause boundary. Pause is supported only before any host attempt, binding or Core session exists. It durably sets observed/desired state to `paused`, keeps the request/message/context and increments epoch. Resume from that state retains those exact identities and pin, checks current account selection, audience revision, project/file rights and transitive source revisions, then queues the same obligation. It does not refresh withdrawn context automatically. Normal claim creates the first native attempt and current lease.

Launched pause returns 501 `contract_unsupported` without changing work. The current Rust shutdown route sends ACP cancel/close and may terminate the child; it does not negotiate a safe pause checkpoint. This slice does not relabel cancellation as semantic pause or claim launched/Project-wide pause acceptance. Launched semantic resume and Core-v1 migration remain separate contracts.

Supplement creates a separate linked obligation under the same bot, lane, account selection, channel audience and project/file selection. The original runtime epoch, pinned context, text, Core binding, partial reply and effects stay intact and may continue. `TaskLink` retains parent request/message, original epoch/pin hash, action, requirement revision and command nonce. The new obligation captures allowed current completed context; it never injects instructions into the active Core session or treats its partial output as completed. This is a bounded compatible supplement contract, not in-place Core replanning. Foreground interjections remain ordinary independent messages.

Replace uses one durable journal event to fence the old work and create its linked successor. The old epoch advances and desired state becomes cancelled; late text, completion and tools under the former epoch are denied. Old history, reply, Core binding and artifact receipts remain retained. The successor starts as `waiting_control_stop`. It is released only when the old status is cancelled, a never-launched proof or matching native stop receipt exists, all old operations are completed, and its current account/context/audience/project/file gates still pass. Unknown effects or unknown process state keep it waiting across restart. No effect is repeated or rollback claimed. Cancelling the waiting successor prevents later release. The successor has a new message/request/Core task; an old final cannot become its final.

This API controls one obligation, not every task in a Project. Supplement/replace on adapter-linked work are unsupported because no new external source-message return binding is negotiated here. Collaboration-stage work is excluded by its typed `Work.Collaboration` binding. Mixed collaboration/control/adapter journal payloads are rejected. Dedicated group cancellation owns group lifecycle. Task controls do not edit goal/participants/budget or revive a group stage.

SSE `task.control` contains `work` plus `taskControl.related` when a successor was created atomically; clients must project both or resnapshot. `work.control_released` reports the subsequent release. Snapshot always contains both obligations. These states/actions require a client capability gate; no frontend changes are included in this patch.

Validation includes nonce/body and two-counter CAS, cancelled/offline rejection, restart, actual filesystem write failure becoming unknown, native PID/session proof fences, source/account/audience/project changes and independent foreground work. The native fixture script records actual Go/Rust/Core evidence separately from typed ledger tests. Local fixture checks are not provider, cloud, physical phone or complete product acceptance.

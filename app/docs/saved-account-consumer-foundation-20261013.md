# Saved-account consumer foundation — 2026-10-13

This adds exported Go, Rust and Core functions for a saved API key. Production execution is still disabled: no CLI, runtime, ledger, API, UI or runtime-pin hook changes are included. Core remains the canonical agent loop. The stored account stays `stored_unverified`; encrypted capsule preparation and `authenticated_probe` never grant execution or establish model readiness.

## Implemented seams

- `connections.SelectConsumer(Pin)` captures only the exact current account revision, credential generation and opaque vault reference. Public JSON omits that reference. Rotation, removal and metadata changes invalidate the selection. `PrivateFrame` is a **probe** frame; it is not the saved-task launch ABI.
- `providerexec.Open/Probe/Receipt` preserves an exact nonce, pin, consent identity/deadline and operation ID in a bounded 64 KiB/128-receipt local journal. It persists `running` before a trusted broker. Restart makes unresolved work `unknown`; no automatic replay occurs. HTTP 401/403 are terminal. 429/5xx allow explicit same-operation retries, at most three. Absent authority, stale/expired consent, transport ambiguity, wrong echoes and storage failure fail closed. This exported probe controller has no production network broker and is not the task ledger.
- `saved_key::prepare` validates the frozen `saved_account_task_v1` private schema, current bounded account catalog, original opaque reference, actor-authorized binding and deadline. `vault::with_secret` DPAPI-opens into a zeroed-on-drop callback buffer. Rust supplies plaintext only through the private broker callback/stdin, checks current authority/catalog again after it, and refuses a response past the original wall or monotonic deadline. Rust does not implement an LLM loop.
- Core `prepareSavedAccountCapsule` writes a purpose-specific AES-256-GCM capsule and HMAC current marker, outside the task state. The public receipt contains only version, capsule ID, binding SHA-256, original expiry and fixture flag. `loadSavedAccountBridge` requires the exact expected binding, capsule ID/private key and mandatory current-authority callback. It creates the existing `NekoConfig`/provider/budget path with no home config, environment credential fallback, project trust, OAuth login or refresh. It checks current authority and capsule before requests/output and cancels silent active requests on revoke. Credential output is filtered and provider errors are payload-free.

The binding fixes account revision/generation/provider/endpoint/model; request/attempt/epoch/fence/context hash; original consent/revision/deadline; and the existing five Core limits. `fixtureOnly` is mandatory and authority-owned. Production requires canonical HTTPS with no userinfo/query/fragment or redirect/proxy widening. Fixture mode only permits an original authored `http://127.0.0.1:<port>/path` catalog endpoint. There is no production TLS bypass or user toggle.

## State and authority

The Go controller is single-service-owner local state. It is not cross-process arbitration, cloud sync or a rollback-resistant secret store. Rust requires canonical existing connections/task directories to be disjoint, and the capsule to be outside both. Core requires a canonical task directory and capsule outside it. Its existing budget file lives only at `stateHome/.neko-core/profile-bridge-budget-v1.json`, bound to the saved binding hash, with no refund after an uncertain request. Capsule/marker writes are individually exclusive/atomic and every incomplete or mismatched pair fails closed; power-loss atomicity of a pair is not claimed.

Current-authority callbacks are mandatory trusted application seams. Metadata, an account pin, vault selection or possession of a prepared capsule is not an authorization source. The next integration must derive them from real Work/current account authority and explicit execution consent; it must not return unconditional true in production. The broker callback/process must enforce the original deadline while blocked; the Rust function independently checks deadline before/after it. JavaScript credential strings are memory-only but complete GC/heap erasure is not claimed.

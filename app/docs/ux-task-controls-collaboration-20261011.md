## Durable local command intent (follow-up from b0c00dc)

This UI-only branch retains an authorized task control, collaboration creation or collaboration cancellation before its first POST. `neko.command-journal.v1` stores at most 16 strict records and 128 KiB of UTF-8 JSON. Each record contains the exact typed command, nonce, original channel/account/project/task counters and file metadata, creation time, a five-minute retry limit and SHA-256 over canonical JSON including the operation kind and cancel route. It does not serialize Work, context, account catalogs, file bytes or excerpts. Recognizable credential/private-key patterns and unknown payload fields are rejected before persistence. A failed storage/hash/lock operation prevents the first POST. The hash detects accidental edits; it is not authentication against same-origin code that can rewrite the record and hash.

Reload restores unknown intent, not a running job. It fetches the snapshot and performs capability-gated read-only receipt reconciliation. It never automatically POSTs a task/group command, changes a nonce, rebinds a selected account/channel/project, renews a retry lifetime, creates a successor or extends the runtime's collaboration budget. A matching applied receipt can reconcile even after local expiry or authority revocation. A missing receipt permits an explicit original retry only while the original counters, scope, authority and local lifetime still match. Unknown, expired, clock-rollback, malformed and stale intents remain reviewable with retry blocked. A command's original goal/text is retained only because replay requires the already authorized exact body; a new draft is not cleared by receipt reconciliation.

`local_command_receipts_v1` and `GET /v1/command-receipts?kind=task_control|collaboration_create|collaboration_cancel&clientNonce=...` (plus `collaborationId` for cancel) are present in immutable runtime source `28ae91010235bc287876922d3d0daa1927f8e005`; the fresh narrow receipt probes and actual local Go UI integration below are now PASS. The additive response is `{version:1,kind,found,clientNonce,input,work?,related?,collaboration?}`. `found:false` is nonmutating and returns no entities. `found:true` identifies the exact original typed input and the current work/linked child or collaboration. Receipt work omits context pins/attempts and file excerpts, so the UI validates proof identity then reads a fresh snapshot and projects the full work from that snapshot. It does not replace full Work with the receipt projection. Legacy capability absence shows an unknown retained intent and makes no unsupported lookup request. The independent runner retains its API_PROPOSED_FIXTURE label for authored metadata responses; this is separate from the actual Go integration. Neither scope accepts native stop proof, Core, provider, cloud sync, physical phone or user visual approval.

The journal uses same-origin Web Locks plus synchronous storage writes to merge other pending records and remove only the proven exact operation. The persisted maximum observed wall-clock value detects backwards movement across reload. It cannot prove real elapsed time against an arbitrarily changed system clock. No new served assets or backend paths are owned by this UI slice; the approved light stylesheet is unchanged.

Validation in progress: exact b0c00dc independent baseline is expected RED (0 PASS / 6 FAIL / 0 BLOCKED), confirming that pending intent disappeared after genuine same-origin reload. The boundary runner is `node scripts/ui_task_controls_groups_local.mjs --journal-boundary true --output <report.json>`; its scope is actual app functions with authored storage/lock/Work stubs in Node VM.

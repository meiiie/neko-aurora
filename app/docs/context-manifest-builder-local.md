# Pure Core context manifest builder

This additive builder targets the immutable Core contract `15654176bc73021030959ca0baabbfe63499c6ce`, starting from App `3309dd3ded89dad671d8d3dd9b193f795896123f`. It introduces no Store, Work, replay, API, host or manager changes. Nothing calls it in production. Core owns its existing agent loop, native journal, compactor and fact authority.

## Trusted input and output

`BuildContextManifest(work, TrustedManifestIntake)` returns a typed manifest, canonical JSON bytes and its SHA256, or `ErrInvalid`. The caller supplies an authenticated exact selection scope, primary owner message and optionally an explicit primary byte range, a live reader catalog record, and unresolved candidates. This struct is a trusted in-process boundary, not a public request body, signature, lease or replacement for authentication. Do not derive it from model output, browser JSON or a quoted prompt.

Normal primary identity/text must exactly match Work.SourceMessageID, Work.OwnerUserID and Work.Text. Shared-channel and direct-routing conversations remain scoped to Work.ConversationID and Publication.AudienceRevision; the selected bot matches Work.BotID. Project identity is null when absent. Publication actor/source/reply channels and the existing ContextPin scope/config/resources/plugin pins must agree. Continuity's recorded ProjectRevision/ChannelRevision preserve the admission provenance at original writing; they may precede current frozen project/audience revisions after an authorized rename/update. The builder retains those positive historical counters verbatim, rejects future counters and does not rewrite them into current revisions. Existing Store live fences still deny old tasks or removed scopes. The original ContextPin digest is verified using its existing Go `json.Marshal` representation with an empty SHA256 field. It is distinct from the Core manifest digest and is not recanonicalized or rebound.

A collaboration stage requires a separate authenticated original group goal identity and matching CollaborationID. The existing durable `Collaboration.created` owner-goal event can supply `Primary.ID = g.ID`, `Primary.SenderID = g.OwnerUserID`, `Primary.Text = g.Goal`, with `CollaborationID = g.ID`. The trusted caller must resolve/validate the authenticated creation event, immutable owner/space/goal and original frozen selection; the server-generated event ID identifies this owner-authored goal even though it has no separate user-message row. Core source kind remains exactly `original-user`; no new enum or replay field is introduced. Primary identity differs from the stage Work.SourceMessageID. The builder verifies that the stage instructions are the exact existing `stageText` of that attested goal. Generated stage instructions are a separate derived source and cannot become original-user authority. Missing goal-event attestation fails; stage text is never a fallback.

Output contains exactly the keys/nulls required by Core admission v1. Core canonical JSON sorts keys using JavaScript UTF16 ordinal order, preserves array order and literal text, and follows JSON.stringify escaping, including raw `<>&`, U+2028/U+2029 and literal backslash-u strings. Go pin hashing remains unchanged. Golden digests and an offline probe use the unchanged admission.ts/wire.ts blobs from Core156.

## Sources and bounds

The full primary text is retained, nonempty valid UTF8, at most 32768 bytes. Its original-user source retains the full byte extent/hash and the exact selected span. Text over 8192 bytes requires an explicit caller-selected UTF8-safe byte range; the builder does not truncate or choose one. All spans are nonempty and at most 8192 UTF8 bytes. Source extent is at most 1 MiB. The manifest is at most 49152 encoded UTF8 bytes, with at most 16 sources and 64 unresolved candidates. Safe integer bounds apply. Any excess fails locally; no source is silently dropped, pruned or reselected.

Pinned prior turns are derived wrappers with explicit user/assistant task-input/reply positions, request/message IDs, bot ID, epoch, sequence and descriptive artifact references. ContextSource does not attest original input authorship or distinguish historical generated collaboration instructions; the input wrapper therefore has senderId null and explicitly marks original authorship as unattested. A user-role task slot does not mint an original-user source. Prior turns are not current-user authority or file bytes. Project name/goal and pinned plugin descriptors are derived metadata. Continuity is a derived literal owner-authored record with confirmed/contested decisions, reference dates/versions, source file hashes/access revisions and URLs. A reference creates no file source or reader grant. No URL is fetched. Dates stay literal within metadata; observedAt/effectiveFrom/effectiveTo are null because current fields do not establish the corresponding canonical source observation/effective interval. Entity IDs remain explicit or null. Labels preserve reference titles; matching names are not merged. Invalid Core entity identifiers fail instead of being renamed. Candidates are validated exact subspans of admitted sources and remain unresolved; none is promoted into facts or semantic memory.

Retrieved sources come only from Resources.Files, the existing selected read boundary. RequestedFileIDs are priority input to existing automatic relevance selection, not the final boundary. The builder performs no selection. Each selected file must retain exact owner/space/project/channel, hash, version, access revision, ready-text status, grant, full extent and UTF8 excerpt. Complete excerpts must match full hash; truncated excerpts retain the authenticated pin's full hash and extent. Only already-selected excerpt bytes are included. The builder reads neither files nor networks.

Files also require explicit ToolPolicyVersion1, the exact pinned `neko-project-sources` descriptor and a matching live trusted builtin catalog record (revision, publisher, version, project.read_file tool and canonical schema). Disabled, mismatched, absent and legacy implicit readers fail. Inline ingestion still needs the live trusted reader. Pure record equality is not proof of a broker operation; Core's matching retrieved observation envelope/native tool receipt is a separate future integration gate.

## Integration gates

The caller must hold the relevant dispatch fence and validate current bot/channel/audience/project/continuity/file ancestry, account lease and live plugin authority before launch and publication. The builder cannot establish current authority from immutable Work alone. Public redacted Work/resources are invalid inputs. Revocation/regrant must not recapture or silently replace an old selection. Preserve frozen collaboration resources or stop the group. Keep manifest admission opt-in and negotiate the new Core/host contract explicitly; do not silently upgrade historical sessions.

The complete actual launch envelope (prompt, existing pins, manifest and metadata) must be checked against the App's 64000 byte bound before commit/dispatch. The 49152 byte manifest limit does not prove the envelope fits. Struct marshaling can expand escaped characters; measure the actual final envelope, even when using the returned canonical JSON as a RawMessage. Durable Core receipt validation and resumed expected session/task/execution/source binding remain required. This patch does not change any launch, journal or receipt field.

## Verification scope

Owned tests cover genuine Store intake/project/file/continuity/shared routing and journal reopen, unchanged input/journal state, role/authority provenance, group attestation, Go pin hashing versus Core hashing, safe bounds/UTF8, reader mismatch/revocation, metadata-only references, redacted inputs, exact unresolved candidates and defensive failures. The offline Node probe runs the original Core156 TypeScript parser/digest against Go-generated manifests and strict negative fixtures; a retrieved observation check is a typed fixture only.

Final code commit, exact commands, environment, file hashes, pass/fail/blocked counts and retained RED/setup failures are recorded in the owned `.build` delivery manifest. This is pure builder/parser and local journal evidence, not native launch, Core compaction/resume, model evaluation, provider, cloud, phone, AT or UI acceptance. Formal Go race detector remains blocked by absent GCC; no tools are installed.

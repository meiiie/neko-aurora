# Local project and source-file contract

This additive slice implements project records, byte-preserving uploads and source pins in the existing Go journal. It does not enable a real provider, external upload, plugin grant, device execution or cloud transport.

`snapshot.capabilities` adds `local_channel_intake_cas_v1`, `shared_channel_context_v3`, `local_projects_v1` and `local_uploads_v1`. `/v1/messages` accepts optional `expectedChannelRevision`, `projectId`, `projectRevision`, `fileIds` in addition to the existing bot/channel/account/nonce fields. New mismatched revisions reject before intake. A duplicate with the original selections returns the same request and current fenced status even after authority changes; it does not restore authority. Omitted channel CAS remains compatible with old clients.

`POST /v1/projects` accepts `{id?,name,goal,expectedRevision,channelIds,clientNonce}` and returns `{project,duplicate}`. Local owner/space and the new project ID are server-derived. Projects permit exact channels; sharing one Project does not import another channel's chat or files. Revision edits fence dependent tasks and require a new intake for the new project version.

`POST /v1/uploads` accepts `{projectId,projectRevision,channelId,filename,contentBase64,clientNonce}`. File bytes are limited to 1 MiB, all stored uploads to 64 MiB and 512 entries. The JSON frame is limited to 1,500,000 bytes. UTF-8 txt/md/csv/json is `ready_text`, with a bounded excerpt and an explicit truncation flag. Other formats, including PDF, are `quarantined_unsupported`; they can be downloaded by the owner but cannot enter a model pin. No parser or application is launched. Credential filenames, private keys and recognized token/credential patterns reject before any write. Pattern screening is a bounded local check, not a promise to recognize every possible secret.

The upload receipt contains immutable ID, filename, SHA256, bytes, MIME, version, status, scope and access revision. The accepted byte file is synced before the journal metadata is committed. An uncommitted same-nonce byte object can be reconciled only if bytes match; it supplies no model authority by itself. Retry with a changed digest or resource selection rejects. Public upload/snapshot/SSE metadata excludes file excerpts.

`GET /v1/projects/{projectId}/files/{fileId}?channelId=...` requires the authenticated local session and matching project/channel scope and current access. It serves attachment bytes only after SHA256/length verification. `POST /v1/file-access` accepts `{fileId,expectedRevision,granted,clientNonce}`; revoke fences tasks that pin the file directly or through prior context. Regrant does not change an existing pin or re-launch it.

Project intake automatically ranks relevant ready documents from the exact project/channel, using task words and filename/text matches; explicit `fileIds` remain possible but are not required. The pin holds exact file hashes/versions/access revisions and bounded descriptive excerpts. Shared-channel pin v3 includes allowed colleague replies within that channel, labels each sender, excludes private/other-channel history, and carries dependency revocation. Historical pin v1/v2 bytes and old refresh event semantics remain replayable.

The Rust host asks Go for current task capabilities after validating the Core operation receipt. `project.read_file` reads at most 4,000 UTF-8 bytes from a file already selected in that task's immutable pin. It validates current epoch, account lease, context/resource authority, exact canonical task/session operation and source bytes. File text cannot authorize another action. Existing `artifact.write_text` keeps its durable intent/receipt and uncertain-outcome fence; external actions remain disabled.

Limits and unsupported formats are intentional local product boundaries. Full document indexing, rich PDF/Office parsing, project decisions/memory editing and cross-channel source declassification require their own implementation and acceptance.

Intake, refresh and linked controls retain the 64,000-byte encoded launch-frame bound. The host accepts text up to 64,000 bytes within its existing 65,536-byte input-frame bound, so a valid 32 KiB request plus pinned sources is not rejected by a narrower host text limit. Historical journal validation is unchanged.

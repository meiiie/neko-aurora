# Two leading tags in a local shared channel

The composer accepts `@Meiiie @Davin Review the release evidence` as an explicit finite collaboration in the shared channel already open. The two aliases must resolve to distinct, active members of that channel. The first alias is the coordinator; the existing runtime runs its proposal, the other bot's review, then the coordinator's conclusion. The existing limit remains three stages and five minutes. The owner goal is `Review the release evidence`; the prefix supplies participants, while a later `@other` inside that goal remains ordinary text.

This is an additive composer path to `POST /v1/collaborations`. A single leading alias keeps the existing `/v1/messages` path, including its same-channel routing and private-lane behavior. The frontend does not fan out messages, import a target bot's private history, create a second owner goal, show generated stage instructions as owner messages, or invent cross-channel delivery. Sending a report to another previously discussed channel still requires a separate typed backend delivery contract and acceptance.

Two-tag intake freezes the current channel ID and audience revision, the explicit selected account ID/revision or no account, the selected project ID/revision, and the existing plugin/continuity selection. The existing collaboration journal captures source-candidate metadata and persists the exact typed body and nonce before POST. The runtime rechecks channel membership, archived participants/project, account, sources and policy at admission. No bot default is silently applied: the collaboration contract has no `useBotDefaults`/per-bot default pin, so that selection shows an actionable reason to choose an explicit account or no account.

Unknown aliases, duplicate aliases, a third leading tag, a malformed second tag, an empty or over-2,000-byte goal, a participant outside the current channel, an archived participant, and a private-lane two-tag request do not fall back to a one-bot message. They show a routing reason and block fresh intake. The second-tag suggestion uses current channel members, excludes the first alias and archived bots, and preserves the already typed first prefix. Mentions after the goal starts do not add participants or reopen participant completion.

The composer reuses `createGroup` and the bounded durable command journal. An equivalent unresolved group body found in that journal keeps its original nonce and directs the owner to read-only reconciliation or the explicit original retry in Work; pressing Send again does not POST or manufacture a new nonce. A matching applied receipt may retire the pending intent after reload; an unadmitted missing receipt permits the existing explicit exact-body retry only while its original scope, counters, authority and local lifetime still match. Reload performs no group POST. Accepted work is still restored from the service's journal rather than browser storage.

A late group ACK updates its original group. It clears the composer draft only if the original view, bot, navigation generation and exact draft still match. It does not select another bot/channel, restore focus, change a newer selection, close a newer dialog or clear a newer draft. The approved Neko Aurora identity, light layout, stylesheet, canonical brand, fonts and Connections secure card remain unchanged.

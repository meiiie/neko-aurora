## Bot preferences

`local_bot_profiles_v1` adds `POST /v1/bots/{id}/profile` with exact `instructions`, `includeHistory`, required `expectedRevision`, and `clientNonce`. Instructions are bounded to 4,000 UTF-8 bytes and screened with the existing bounded secret pattern. This is a behavioral preference, never a capability, file permission or audience grant. Revision zero means empty instructions and completed-conversation history enabled.

The event is durable and strict; create, rename and profile commands cannot reuse each other's nonce. Duplicate configuration receipt returns current configuration while retaining the original intent. A new request pins the current profile in Work and context pin v4; legacy v1/v2/v3 pins remain byte-compatible. Existing work retains its pin even after a profile change or explicit context refresh. A linked supplement/replacement and each newly admitted collaboration stage are new requests, so they pin preferences at their own creation time. This does not repin the whole collaboration plan or resume old work.

The composer menu opens “Hướng dẫn & lịch sử của bot.” The history checkbox excludes completed requests in that exact conversation from new intake. It does not delete visible history, disable Core's internal task/session state, disable permitted project files or owner continuity, or import another bot's private history. Model/account defaults, archive/delete, and new-conversation boundaries remain separate gaps. Browser command retry is page-lifetime memory; server configuration and receipts survive restart.

New message clients can send optional `expectedBotProfileRevision` under `local_bot_profile_intake_cas_v1`. The server compares it to the routed target bot, records the original expectation and checks it before accepting a new request. A stale expectation returns 409; a duplicate requires the exact original expectation and keeps the old pin. Browser outbox/retry freezes this field, including for a leading @alias. Older callers without this optional CAS retain their existing default-selection behavior.

## DOCX and text preview

The stdlib-only DOCX parser's limits and security checks are recorded in [the extractor contract](local-docx-extraction-20261012.md). DOCX text ingestion records extraction version 1, format `docx_ooxml`, full-text SHA-256 and UTF-8 byte count separately from the original file SHA-256/byte count. Original downloads retain exact uploaded bytes. Malformed, unsafe, empty or unsupported packages remain quarantined. The full extracted text is screened before any ready-text journal commit; only a bounded UTF-8 excerpt is retained. This is bounded in-process parsing, not an OS sandbox or general Office/PDF/media support.

Runtime source pins and read ranges use the extracted text identity and offsets for DOCX. Every broker read rechecks original physical bytes, re-extracts under the same limits, and verifies the full extracted identity. Context manifest text provenance uses full-text hash/bytes; Work's resource pin retains original-file provenance. Missing or changed physical bytes block that read without corrupting unrelated journal replay.

`local_file_text_preview_v1` exposes authenticated read-only `GET /v1/projects/{project}/files/{file}/text?channelId=...&projectRevision=...&accessRevision=...`. Exact scope, project revision, live grant and access revision are required. Response contains at most 16,000 UTF-8 bytes, text hash/size, truncation and public file metadata. Browser preview uses textContent only, keeps no excerpt in localStorage, clears on close/scope change/revocation and fences delayed responses. PDF and other Office/media formats, retention/export/share and broader sandbox preview remain missing.

## Two local client simulation

`local_sync_simulation_v1` and authenticated GET-only `/v1/local-sync?botId=...&channelId=...&projectId=...&cursor=...` integrate [syncstream v1](local-sync-envelope-20261012.md) with an atomic journal projection. A durable random `local-sync.identity` binds cursor continuity across service restarts. It is an identifier, not a credential. The existing local session cookie/Host/Origin boundary remains required.

The immutable scope digest binds local owner/space, selected bot and exact conversation/project, current audience/project revisions and changed file-access revisions. Authority changes require a new scoped snapshot/client rather than automatic rebinding. A global excluded event still yields an empty frame. Object revisions are their last projected global event sequence plus one; built-in bots start at one, avoiding a collision with a rename at journal sequence one. Complete snapshots and increments use the same captured high-water state under the store lock. Oversize entities/snapshots fail explicitly rather than silently truncating a complete replica.

Projection includes bot display metadata, published user/assistant text and file metadata only. It omits raw file content/excerpts, secrets/account pins, task/runtime manifests, private context, internal collaboration instructions and command nonces. Collaboration exposes one owner goal and only its final stage reply/files. File metadata/receipt presence is not readiness, bytes or an execution/read grant. The narrow reference clients demonstrate local reconciliation, not cloud transport, pairing, multi-owner authentication, remote devices or installable phone lifecycle.

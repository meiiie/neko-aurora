# Published result as destination Core context

Baseline delivery `ce6d0f4239cbd21aa11cd0ad608bc3f99bd25bee`, application `2a740296e0711989d82601ac09a247bf2a5fa86c`. The owner publishes a private completed report into a shared channel, then asks a channel member or the existing finite two-bot group to discuss it and finish a follow-up. Core must receive only the published result and selected output files, never source chat/private context or unpublished files. User authorization covers this implementation and local fixture tests, without new provider secrets/grants/deployments.

## Choices

| Shape | Consequence | Decision |
|---|---|---|
| Dedicated PublishedReportPin in ContextPin5 | Pins result/provenance/destination/publication at intake; direct and recursively derived readers can revalidate current delivery authority. | Selected. Does not impersonate source Work as local history. |
| Copy private Work into existing ContextSource | Existing history serialization carries Text, Reply and all artifacts; identity is a private request and same-conversation guard would need relaxation. | Rejected: violates the disclosure boundary. |

The pin contains delivery/message/publication sequence, publisher bot, exact destination/audience, public result Reply, selected artifact descriptors, public source provenance and its digest. Source prompts, private profile/history, resources, operation payloads and internal all-artifact pins are excluded. Context versions1-4, historical plugin/default selection and hashes remain unchanged. New shared intake uses version5 only under the new contract. IncludeHistory=false remains effective. Bounded combined history/report budget and existing manifest/prompt limits apply; omission is explicit rather than unbounded context.

Groups freeze a typed PublishedReportContext at group creation, with its sequence/pins/omitted count. Every generated stage inherits those exact pins and keeps the original owner goal. It never picks a newly published result during continuation/retry. Old groups without the field keep their historical context behavior. Stage summaries are ordinary derived history, so recursive context checks must carry the original report dependency even if the report itself is omitted by later bounds.

## Read and authority

The current publication must remain active under source/result/resource access and destination membership/revision. A consumer may be Davin while the publisher is Meiiie; both are checked as current members of the exact destination. Publication does not grant private-source history access. Recheck at intake, claim/admission, tool read and completion. Revoking source or destination authority suspends dependent queued/running tasks and stops further group stages; regrant does not refresh old pins automatically.

Selected output bytes are read through `report.read_artifact` with exact delivery/artifact pin plus bounded UTF-8 offset/range. No global ReadArtifact, filesystem path or arbitrary source artifact fallback. This reader is a distinct trusted builtin under ToolPolicyVersion2, with pinned revision/schema and current plugin policy. Version0/1 builtins/default selection remain unchanged. An explicit selection cannot silently acquire a reader that the owner omitted. Disabled/revised reader policy revokes admitted read capability.

The existing seven-field Core launch protocol and version1 admitted ContextManifest are retained. Published output appears as a typed descriptive derived manifest source in the destination scope; it is not another original-user command. Selected file pins include only the verified original output's first bounded UTF-8 span (at most4,000 bytes), original descriptor/hash and public provenance. The runtime manifest attests that span as retrieved descriptive content, deduplicating exact repeated file identities across publications. An inconsistent repeated identity fails closed. Under this unchanged Core protocol, a read outside the admitted span is refused; this slice does not claim unrestricted large-file reading. File observations keep the existing seven-field result and admitted read-envelope shape. Report instructions cannot expand recipients, sources or tools.

The new reader's reserved plugin ID can collide with a genuinely older unverified/disabled descriptor. New plugin lifecycle journal writes carry internal catalogVersion2; historical missing-version import validation preserves the older catalog. Existing descriptors remain untrusted and shadow the reader rather than being overwritten or silently upgraded. Default context still receives the permitted report Reply, while file reading remains unavailable in that collision. Historical update/remove records remain valid; a current new import cannot shadow the reserved builtin.

Completed derived replies/files and report-derived group projections must mask stale content as well as fence execution. Store-aware public projection applies to snapshot, API/receipt, events, shared export and local replica. Stale Store.Snapshot work also drops its derived RuntimeContext; collaboration snapshots omit frozen report pins. Internal Get/group records and durable journal bytes remain unchanged. HTTP PublicSnapshot already omitted these fields; the independent finding concerned the internal snapshot contract. Owner-wide source Work/profile access remains the existing single-owner boundary; no multi-human privacy claim is added.

The actual retained Core initially refused the new reader because its trusted observation verifier recognized only project.read_file. Core needs a narrow report.read_artifact verifier bound to the authenticated publication source and selected retrieved span, with the existing exact-result and restored-tool-pair checks. The provider fixture must request the exact admitted byte span, rather than the tool's maximum range. Historical binaries and failed runtime receipts remain preserved; the new Core candidate must be validated and pinned separately before integration acceptance.

## Throughput and verification

- Blocking first steps: protect current release/ZIP/raw files, inspect actual context/tool paths, settle typed pin and historical policy boundary.
- Independent workstreams: one Go owner for context/reader/projection/tests; Root for native story/provider fixture and integration; bounded independent composition review; separate media-only Library save.
- Shared state: Root alone stages/commits/Main updates. Backend owns Go; Root owns fixture/design files. State/profile/cache/media use separate E scratch paths.
- Smallest safe decomposition: typed pins, versioned reader, one native single/group story and one independent composition suite. No broad repeated audit or new remote transport is bundled into this slice.

Native acceptance uses genuine Go/Rust/Core processes and a controlled loopback provider. The report itself is produced through Core/tool calls; the later member reads its admitted published context/file and completes a follow-up. Two-bot stages must observe the same published report and previous permitted stage output, with one final writer. Probe private/unpublished canaries, exact read hash/bytes, forged reads, source/plugin/audience revocation, ACK-loss duplicate and restart. These tests establish protocol/lifecycle/context behavior, not real-model reasoning, production provider quality, Tauri/phone/AT or cloud.

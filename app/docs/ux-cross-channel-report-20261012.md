# Report delivery into the current shared channel

The requested story is `@Meiiie gửi báo cáo đã làm ở cuộc trò chuyện riêng vào kênh này`. The current shared channel is the destination. The human request supplies sufficient delivery intent; it does not require a file picker or another approval. Source selection belongs to the Go control plane. A uniquely related completed report may be delivered; an ambiguous selection produces one short question asking for report detail. The frontend never chooses a source by browsing private prompts, context or history. The question has a normal inline `Trả lời câu hỏi này` action. It pins visible reply context in the existing routing note, with `Bỏ trả lời`; the owner can then answer just `Atlas`. Navigation or a new leading bot tag clears reply context, while any already pending durable intent remains pinned.

The existing Tauri renderer keeps the approved Neko Aurora identity, light layout and palette. A single leading bot alias plus a report/private-conversation/current-channel delivery phrase takes a dedicated typed command path. Ordinary single-tag messages, internal mentions and the two-tag finite collaboration path retain their existing routing. The parser must reject a recognized report-delivery request when its shared destination or member is unavailable rather than silently turning it into an agent task.

## Existing lifecycle and integration boundary

`app.js` prepares ordinary messages with channel/audience, account, project, profile, bot-state, policy and nonce pins. The bounded local message outbox persists that body before POST. An ACK only retires the matching original body and pins. Definitive rejected entries are skipped so later valid messages may continue. Outbox retry behavior remains the ordinary-message contract.

The separate command journal canonicalizes typed commands and scope, hashes the persisted material, coordinates writes with a browser lock and retains a five-minute original lifetime. On reload it performs read-only receipt reconciliation. Its original nonce and body are preserved for explicit retries after the service reports a missing receipt. Navigation, newer drafts, dialog state and focus remain independent from late ACKs.

Snapshot sequence and server-sent events restore accepted service work. A sequence gap causes a fresh read-only snapshot. Report delivery must participate in this restoration, with an immutable public receipt and public projection; reload must never POST a report automatically.

The typed first request is exactly `{botId,destinationChannelId,expectedDestinationRevision,clientNonce,text}` at `POST /v1/report-deliveries`. A short clarification answer adds only `clarificationOf`, the original public question ID, and carries the exact human answer with a new nonce. The source result remains server-selected. The body is persisted before POST in the existing bounded, hashed journal. `GET /v1/report-delivery-receipts?clientNonce=…`, `Snapshot.reportDeliveries` and `Event.reportDelivery` restore public delivery state. Artifact links use `/v1/report-deliveries/{id}/artifacts/{artifactId}`. No synthetic Work object or runtime task is created.

The durable record contains the human request, bot, current destination revision and optional public question reference only. It does not contain private source text, an account, project, grant or candidate-source list. The first request is at most 4,096 UTF-8 bytes on one line. A reply topic is at most 256 UTF-8 bytes and 12 words, excluding recipient/file/permission directives. A consumed public question has `answeredBy`, is inactive and shows `Đã trả lời câu hỏi báo cáo`; its reply action is hidden. A delivered projection displays only the requested completed report reply or artifact and safe provenance. A clarification projection displays only its minimal question.

Any authority/dependency event, an unknown or changed Work event, or an SSE sequence gap synchronously masks report content and links before a read-only resnapshot. A failed resnapshot keeps the report masked. A known running `work.text` event may bypass this fence only when its exact envelope is recognized, its reply is an append-only UTF-8 string of at most 65,536 bytes, and every other Work field matches the previous public record. This preserves reports during unrelated background text streaming without admitting a changed source pin, status or authority. Both ordinary ACK acceptance and durable receipt reconciliation verify a fresh public snapshot; an old successful receipt cannot restore source content after revocation. Previously read text cannot be removed from a person's memory; this is a current rendering and download fence.

## Fixture and acceptance plan

The owned runner is `scripts/ui_cross_channel_report_local.mjs`. Source-function checks will exercise the actual parser/dispatch and durable validation functions. The browser gate will use actual locally compiled Go assets and real headless Chrome with a disposable loopback fixture; source and served asset SHA-256 hashes, exact commit, command, environment, binary VCS metadata, every pass/fail result and cleanup will be recorded.

The exact story will be exercised at desktop and emulated mobile sizes. It must yield one delivery command, one requested report result with provenance in the original shared destination, no private source prompt/context/history canaries in the destination projection or rendered report, and no file picker or approval dialog. A second related completed report must cause a minimal question, with no candidate report content published. Fault checks cover committed ACK loss, receipt-only reload, unadmitted command loss with explicit exact-body retry, stale destination revision, archived/nonmember bot, late navigation/draft/focus fences and ordinary-message progress after a rejected outbox entry.

Actual Chrome screenshots and a short recording of the story will be saved under `E:/CodexScratch/cross-channel-report-20261012/ui`. The browser profile, disposable service state, fixture source journal and temporary files stay outside transferable evidence. These checks are local delivery and browser acceptance; they do not claim cloud sync, a provider/model evaluation, a native Tauri window, physical-phone acceptance or assistive-technology speech.

# Local context reuse permission and suspended obligations

The local owner can change whether a source request and its answer may be reused as context. POST /v1/context-access accepts requestId, expectedRevision, granted and clientNonce. Source access defaults to granted at revision zero for existing records. Each committed change advances the source revision; nonce retry is idempotent and a conflicting revision is rejected. This is a local context reuse control, not a provider grant, connector ACL or deletion of the owner's retained history/files.

New pin v2 retains each source access revision. The accepted bytes and hash remain immutable. Claim, admission, text, completion and new tool effects check current source revisions and their transitive ancestry under the journal mutex. Regrant advances the revision again and never makes an old pin valid. New intake excludes revoked sources, derived answers with invalid ancestry and unresolved effects. Replay retains the original v1 selector for historical v1 pins, including the old completion bug; it does not reclassify a previously accepted journal as corrupt.

An invalid queued obligation becomes suspended. A launched obligation becomes suspending and the manager closes its host input; new output and effects are already fenced by the durable source change. A crash between source change and lifecycle events cannot bypass the gate. Startup finishes the missing suspension events. An obligation with unknown process state stays suspending and its Core binding remains intact. Receipt reconciliation remains independent of the task lifecycle and never repeats an unresolved effect.

The trusted Rust host closes/cancels the admitted Core session, stops its owned native child and emits runtime_stopped only after a successful process wait. Before checking the admission permission gate, Go durably records RuntimeAttemptBinding from that attempt's validated native admitted event. A resumed binding must retain the saved session, task root/id, runtime hash and execution authority, and advance activation by one. This receipt path does not replace the saved Core binding or admit model output/effects. It allows a valid current child stop receipt after permission revocation rejects admission. A failed resume without validated binding cannot substitute its new PID for an unknown saved Core. Closing the Rust pipe or waiting on a WSL supervisor alone is insufficient. Late stop receipts from a previous attempt are rejected; claim clears the previous proof and attempt binding. Unknown or malformed shutdown cannot enable context refresh.

POST /v1/context-refresh accepts requestId and expectedEpoch. It requires suspended work, its own source access granted, no tool operations, fewer than four archived attempts, and a durable native stop receipt or proof that the work never launched. Intake and refresh share the 64000-byte encoded prompt bound, including JSON escaping; an oversized refresh leaves the existing obligation and journal unchanged. The owner explicitly accepts a fresh context attempt. The same request/message/obligation is retained; epoch/context revision advance, current Core binding is cleared, and the old binding, reply and pin hash remain in an archive excluded from the model prompt. A new Core task/session is used because the old checkpoint contains withdrawn context. This is not a fallback for forced-crash recovery. Work with effects or unknown process state cannot take this path.

Snapshot capabilities context_access_v1 and context_refresh_v1 let the UI hide these controls against older servers. The UI must still handle revision/epoch conflicts. A valid local permission never authorizes publication into another audience or channel; cross-channel provenance and read/publication ACL remain separate blocked gates.

New context refresh events carry contextRefreshVersion 1. Historical unversioned refresh events remain readable even if the earlier development runtime accepted an oversized encoded prompt. Startup suspends only that unlaunched obligation with context_prompt_oversized; its accepted pin, archives and request identity remain unchanged. Claim and dispatch reject oversized initial prompts. The owner can withdraw a large source and explicitly refresh again; the service never rewrites the accepted context or treats this task-local bound failure as global journal corruption.

Verification covers queued and transitive invalidation, regrant, immediate output/effect fences, a crash between access and lifecycle commits, native receipt identity/attempt fences, immutable archives, unresolved effects and historical v1 replay. scripts/e2e_permissions.py exercises actual native Windows Core through an owned loopback provider. Fixture results do not prove model quality, cloud delivery or phone behavior.
